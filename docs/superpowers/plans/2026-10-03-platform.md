## Phase 1: developer foundations

### 1.1 OpenAPI 3.1 spec and an interactive API reference
- The spec lives next to the handlers: each route in `backend/internal/api/server.go` registers its request and
  response types; a generator walks the route table and the Go types (reflection over the JSON tags already used)
  and writes `backend/openapi.json`. A test fails when a route exists without a spec entry or a spec entry has no
  route, so the docs cannot drift.
- Served at `GET /v1/openapi.json`; an interactive reference page (Scalar, MIT) at `/docs` on the website, branded,
  with "try it" against the live API and the wallet-signed request recipes.

### 1.2 `@cargoflow/sdk` (TypeScript, isomorphic, npm)
- New workspace package `packages/sdk` (pnpm workspace at the repo root; ESM + CJS builds with type declarations via
  tsup; Node 18+, browsers, Workers). The web app switches to it so there is one implementation.
- Modules: `api` (typed client generated from the OpenAPI spec), `contracts` (ABIs + viem read/write helpers for all
  seven contracts and CoverPool), `gateway` (Ed25519 key, signing string, request signing, key files), `messages`
  (every wallet authorization message, byte-identical to the backend, pinned by shared vectors), `csv` (logger
  parsing), `evidence` (epoch aggregation and the Poseidon leaf/Merkle construction).
- Note on Merkle roots: leaves include a per-reading salt derived from the operator's secret, so only the operator
  (or a gateway holding its own salts in a future mode) can recompute a committed root. The SDK exposes the
  construction and verifies roots and inclusion proofs when salts are supplied; it does not pretend to recompute
  operator roots without them.
- Transactions are returned as plain requests `{to, data, value, chainId}` for any wallet to sign; EIP-712 is used
  only for typed signatures, not for transactions.

### 1.3 CargoFlow MCP server (`@cargoflow/mcp`, npm, stdio + Streamable HTTP)
- Built on the SDK with the official MCP TypeScript SDK. No private keys, ever.
- Read tools (no auth): `list_shipments`, `get_shipment`, `explain_shipment`, `get_evidence`, `get_track`,
  `get_party`, `list_market_requests`, `get_cover`, `verify_document` (hash a local file and compare).
- Prepare tools (return unsigned transaction requests plus a CargoFlow web link that opens the same action ready to
  sign): `prepare_deposit`, `prepare_release`, `prepare_resume_with_proof`, `prepare_mark_delivered`,
  `prepare_settle`, `prepare_open_dispute`, `prepare_offer_cover`.
- Gateway tools (only when the user configures a gateway key file path locally): `submit_readings` from a CSV.
- Resources: `cargoflow://shipment/{id}`, policy and contract addresses. Prompts: "Daily fleet risk review",
  "Explain this pause".
- Listed in the MCP registry and README with one-line install for Claude Desktop, Claude Code and Cursor; a hosted
  read-only endpoint on the backend at `/mcp`.

## Phase 2: edge ingestion and automation

### 2.1 Gateway agent (`@cargoflow/gateway`, npm CLI; also a single binary)
- `cargoflow-gateway init` (creates or imports a key file, registers via a wallet link), `watch <folder>` (new or
  changed logger exports are parsed, de-duplicated and sent in signed batches, with an offline queue and retries),
  `mount` mode for USB mass-storage loggers (detects the volume and reads its export), `serial` mode for loggers that
  stream over USB serial.
- Parsers: generic CSV (existing mapping), and vendor presets written from the vendors' published export formats
  where available (Sensitech TempTale, Elitech RC series, ELPRO LIBERO). Each preset ships with a fixture; presets
  without a verifiable sample format are marked experimental.
- Runs on Raspberry Pi (arm64), Linux, macOS, Windows; systemd unit and Docker image.

### 2.2 Automatic ZK recovery worker
- Backend job: when a facility is paused and a probe has 8 fresh in-range readings after the pause, it prepares the
  recovery for the exporter's wallet (existing `PrepareRecovery`, bound to the exporter as submitter), stores the
  calldata, and notifies the exporter (Telegram, email, webhook, in-app) with a one-click "Review and sign" link.
- Today preparation needs the exporter's signed request to protect the worker's gas; the worker instead commits only
  when the exporter opens the link (signature then), but pre-computes the witness and proof so signing is instant.

### 2.3 Alerts and webhooks
- Already built (webhook with HMAC, Telegram, email). Add an in-app notification centre and Slack incoming webhooks.

## Phase 3: enterprise and financial hardening

### 3.1 Hardware-rooted device trust
- Gateways may sign with P-256 (ECDSA) keys held in secure elements (Microchip ATECC608A, Nordic nRF91 series) or
  in phone secure enclaves through WebAuthn passkeys (works with no extra hardware: a phone becomes a signed
  inspection device).
- Device registry: a manufacturer or operator certificate chain (X.509 attestation) is uploaded with the device;
  the backend verifies the chain and the device's attestation, stores the device class ("secure element",
  "passkey", "software") and the evidence engine weights source reliability by class.
- On chain: a `DeviceRegistry` contract records device key hashes and their class so anyone can audit which sources
  fed an epoch (contract v3 item).
- Needs: one real secure-element board for an end-to-end hardware test; the passkey path needs nothing.

### 3.2 Trade standards
- GS1 EPCIS 2.0: export every shipment's events (commissioning, shipping, sensor observations aggregated per epoch,
  receiving) as EPCIS 2.0 JSON-LD with the standard sensor-element extension; `GET /v1/shipments/{id}/epcis`, a
  download on the dashboard, and an EPCIS capture endpoint to import events from an ERP.
- Electronic bill of lading: an `EBLRegistry` ERC-721 contract (v3) where each token is one bill of lading
  (document hash, issuer, shipper, consignee, possession history). A facility can be bound to an eBL; financing
  and settlement follow the holder of the title, and surrender at delivery is recorded. Wording: "designed around
  MLETR concepts (exclusive control, singularity, integrity)", not a legal compliance claim; legal recognition depends
  on the jurisdiction and on a reliable-system assessment that code cannot grant.

### 3.3 Account abstraction with passkeys and sponsored gas
- Research spike first: whether an ERC-4337 EntryPoint (v0.7), a bundler and a paymaster exist on Robinhood Chain
  Testnet (46630), or whether Privy / Pimlico / ZeroDev support it. If none, self-host: deploy EntryPoint v0.7 and a
  verifying paymaster ourselves and run an open-source bundler (e.g. Alto) next to the backend.
- Then: smart accounts with passkey signers for buyers, warehouse receivers and arbiters; `markDelivered` with a
  fingerprint; gas sponsored by the paymaster within limits.

### 3.4 Pricing and parametric cover
- Risk-adjusted fee guidance: a pricing service suggests a fee band per request from the exporter's track record, the
  route's historical excursion and conflict rates, the cargo template and the cover status; shown in the market and
  offer flow with the reasons. Financiers still choose the fee.
- Parametric cover (contract v3, extends CoverPool): a cover can carry a trigger "temperature outside the band for
  more than N consecutive committed epochs" read from the EvidenceRegistry; when met, the pool pays the financier's
  outstanding principal and an agreed salvage amount to the exporter, without waiting for a default.

### 3.5 Python SDK (`cargoflow`, PyPI)
- Analytics first: pandas/polars data frames of shipments, epochs, decisions, conflicts and payouts; portfolio
  exposure, excursion statistics, conflict distributions, Monte Carlo of default and recovery using historical
  epochs; example Jupyter notebooks. Read-only plus gateway signing; no transaction submission.
